## 1. 建议与产品范围

建议采用一个 Rust 共享核心、两个原生应用和各自的系统小组件。macOS 使用 SwiftUI + AppKit，Windows 使用 C# + WinUI 3。直接从现有代码提取核心，现有 Tauri 客户端保留作行为参考，不要求再接入新核心，也不作为新版本发布的前置条件。

“原生”在本计划中表示界面和系统集成使用平台框架。Git 仍由共享 Rust 核心通过受控参数调用用户安装的 Git。更换 UI 不需要同时改用 libgit2，也不需要分别用 Swift 和 C# 重写 Git 行为。

| 交付物 | macOS | Windows |
| --- | --- | --- |
| 完整应用 | SwiftUI 仓库列表、筛选、操作和设置；AppKit 管理窗口与菜单栏 | WinUI 3 仓库列表、筛选、操作和设置；Win32 管理托盘等集成 |
| 系统小组件 | WidgetKit，小/中/大尺寸 | Windows Widget Provider + Adaptive Cards，显示在 Widgets Board |
| 快捷入口 | 菜单栏状态菜单 / 弹出面板 | 系统托盘入口与正常原生窗口 |

系统小组件首版提供小 / 中 / 大尺寸，显示全部仓库摘要、需要关注的仓库和最后成功读取时间，并通过深链打开应用。仓库分组和筛选在完整应用中实现；每个小组件实例的自选分组放到后续版本，避免首版同时实现 App Intents 配置与 Windows 自定义流程。Pull / Push 从小组件进入应用后再确认执行。

小组件的添加、移除、布局与展示位置由系统宿主管理。应用设置只提供配置说明和适用的系统入口，不承诺一个跨平台开关能直接添加或移除用户固定的小组件。完整应用采用正常原生窗口，不实现 WorkerW 贴附、特殊桌面窗口层级或跨 Space 常驻效果。

系统版本下限由阶段 0 选定的稳定版 Xcode / SwiftUI / WidgetKit、Windows App SDK / .NET 及所用 API 的正式支持范围共同决定，并写入构建配置和发布说明。macOS 14 是系统桌面小组件的功能下限参考；Windows 侧以 Windows 11 Widgets Board 为产品前提，不据此直接承诺所有 Windows 11 构建均已验证。选用 API 要求更高版本时提高下限，不补旧系统替代实现。

首批构建目标沿用 macOS arm64 / x86_64、Windows x64；阶段 0 核实工具链支持和测试设备。若当前工具链无法覆盖某个目标，调整发布矩阵，不引入旧工具链兼容分支。Windows ARM64 为后续独立目标。

当前并非只需更换 React 渲染层。刷新服务直接持有 `AppHandle` 并更新托盘、写 Widget 数据、发送 Tauri 事件；设置路径依赖 Tauri；部分动作规则仍在 TypeScript 中。这些是共享核心的主要拆分点。

现有 DTO 把 `error` 编码到 `relation` 中，也包含 `changeLabel` / `hint` 等展示字符串。新契约不承担旧 DTO 兼容：区分五种 Git 关系与读取失败，传递 ahead / behind 等已有结构化信息，原生 UI 负责文案和格式。只重整表达与边界，不趁机扩展 Git 功能。新设置也不保留 `allowWidgetDrag`、`compactMode` 等不适用于原生产品的历史字段。

## 3. 必须修正的平台假设

旧的 `NATIVE_WIDGET_IMPLEMENTATION_PLAN.md` 中“Windows 没有第三方 Widget API”的结论已过时。Microsoft 已提供 Widget Provider API，但官方 Widgets 的宿主是 Windows 11 Widgets Board，不能据此承诺与当前贴桌面窗口相同的体验。[Microsoft：Widgets overview](https://learn.microsoft.com/windows/apps/design/widgets/)、[Widget providers](https://learn.microsoft.com/windows/apps/develop/widgets/widget-service-providers)

WidgetKit 支持版本和“系统桌面可放置小组件”需要分别说明。macOS 桌面小组件是 WWDC23 引入的系统体验；原项目的 11.0 deployment target 不作为新应用必须继承的约束，实际下限按阶段 0 选定的 API 和工具链确定。[Apple：Bring widgets to new places](https://developer.apple.com/videos/play/wwdc2023/10027/)

WidgetKit 扩展并非持续运行的应用。时间线更新由系统调度，存在刷新限制。因此应用面板负责及时反映扫描结果，小组件展示最近一次成功快照及更新时间；“调用 reload 后固定几秒内显示”不能作为系统保证。[Apple：Keeping a widget up to date](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date)

当前 macOS Provider 读取 `~/Library/Application Support/GitaView/widget-data.json`，扩展 entitlements 为空。代码存在不等于已证明该文件在正式签名、扩展运行环境下可读。原生版本计划使用 App Group 容器，在主应用和扩展中配置匹配的权限与签名，并在真实安装环境验证。[Apple：Configuring app groups](https://developer.apple.com/documentation/xcode/configuring-app-groups)、[Accessing app group containers](https://developer.apple.com/documentation/xcode/accessing-app-group-containers)

## 4. 目标架构与调用边界

建议目录如下；直接提取核心并运行已有业务测试，不要求先改造一次旧客户端。

```text
crates/
  gitaview-core/          # 模型、Git、配置、刷新调度、应用服务
  gitaview-ffi/           # C ABI、句柄、缓冲区和可关闭的快照等待
apps/
  macos/                 # SwiftUI + AppKit + WidgetKit extension
  windows/               # C# WinUI 3 + Widget Provider
contracts/
  fixtures/              # Rust / Swift / C# 共用的新契约样例
src-tauri/               # 现有实现参考；新应用不依赖此壳
src/                     # 现有 React 交互与业务样例参考
```

共享核心负责仓库管理、状态读取、操作校验、设置一致性与刷新。应用宿主负责文件选择器、窗口、菜单栏 / 托盘、开机启动、打开目录 / URL、系统小组件通知和平台生命周期。文件路径、日志位置、共享快照位置由宿主注入。

每个用户会话只运行一个负责扫描与设置写入的应用实例。关闭窗口继续驻留菜单栏 / 托盘；选择“退出”才结束核心。首版不增加系统服务或常驻守护进程。应用完全退出后，小组件继续显示带时间标记的历史数据，并提供打开应用入口。

小组件后台进程不持有扫描引擎，也不因系统唤起而自动启动扫描。首版只在主应用存活时产生新的仓库状态；独立于主应用的后台扫描不在范围内。Widget Provider 按系统生命周期运行，不以主应用退出作为它必须立刻退出的条件。

### 跨语言接口

首版建议采用窄 C ABI + 版本化 JSON 数据，而不是直接跨边界传递 Rust 类型。macOS 链接 Rust `staticlib`，Swift 通过 C 头文件调用；Windows 加载 `cdylib` DLL，C# 通过 `LibraryImport` / P/Invoke 封装。Microsoft 的互操作文档建议适用时使用 `LibraryImport` 和 `SafeHandle`。[Microsoft：Native interoperability best practices](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices)

接口设计要求：

- 初始化传入数据路径与宿主能力，返回不透明引擎句柄；引擎使用独立于 UI 的线程处理刷新。
- 对外仅暴露仓库管理、快照、刷新和 Fetch / Pull / Push 等白名单操作，不提供任意 Git 参数或 shell 执行入口。
- 首版 Git 操作接口使用明确的函数参数和同步返回结果，由 Swift / C# 工作线程调用，再将结果交给各自 UI 主线程。不额外建设通用任务 ID、结果查询库和操作事件总线。
- 状态刷新提供请求刷新、读取最新快照、等待状态变化三个接口。慢消费者可跳过中间结果；等待使用 sessionId + stateRevision，generation 单独标识已接受的扫描结果。刷新请求返回 requestId，完成看 completedRequestId，不能把返回成功当成扫描结束。等待必须能被关闭请求唤醒。
- 明确 UTF-8 编码、字节长度、整数宽度、缓冲区释放函数、句柄有效期和 ABI 版本检查；阻止 Rust panic 穿越 FFI 边界。
- UI 主线程不等待扫描或网络操作；Swift / C# 不直接释放 Rust 分配的内存。
- 新应用与 Widget 快照统一约定时间单位和解码方式，使用 Unix 毫秒时间戳及各语言的显式转换，不继承两套历史时间编码。契约包含 schema 版本；与新版本自己的持久快照不匹配时显示重新打开应用的提示。
- 返回稳定错误码和必要上下文，由各 UI 负责呈现。新调用契约无需保持旧 Tauri 命令的参数、错误字符串或 JSON 字段兼容。

生命周期必须实现 `Running → Stopping → Stopped`：进入 Stopping 后拒绝新操作、停止定时器，不再派发新的仓库扫描或 Git 命令，并唤醒所有快照等待者。宿主保留引擎与 DLL / 静态库的有效期，直到所有 FFI 调用返回并回收线程后再销毁句柄。

正常退出允许已开始的 Git 命令完成，UI 提示正在退出且不阻塞主线程；不把安全取消 Pull / Push 作为首版承诺。保留现有单次本地 Git 命令 30 秒、网络命令 600 秒的超时处理，不能据此承诺整个扫描或退出只需要 30 秒。超时终止或操作失败后请求重新读取状态，因为 Git 命令可能已经改变本地或远端；不自动重试写操作。进程崩溃或系统强制结束属于异常终止，需用下一次启动扫描恢复真实状态。

不把 UniFFI 引入首版作为必要依赖。若手工绑定成本在原型中明显过高，再评估生成绑定，并同时验证 Swift 和 C# 的实际工具链。

### 刷新和操作一致性

保留现有一次扫描、请求合并、快照代数和设置保存冲突检查。把 Git 操作结束后的刷新请求放进应用服务，成功和可能有部分副作用的失败都重新读取状态；若已进入 Stopping，则由下一次启动完成重新扫描。菜单栏 / 托盘、应用面板与小组件写入都消费同一份结果。

配置落盘成功后立即更新可见投影：删除项消失，分组计数更新，新增仓库为 pending；随后扫描失败也不能复活已删除记录。配置提交、刷新开始和结果完成都通知订阅，但只有被接受的扫描完成结果增加 generation。保存失败保持内存和 revision 不变。完整字段、请求合并及错误返回见实施说明，正式绑定前固定 schema。

发布顺序为：完成核心快照并唤醒等待者 → 平台适配器消费快照 → 写入 Widget 数据并通知系统。文件写入、UI 主线程调度或系统 Widget API 失败不能卡住核心的快照完成与后续刷新。共享排序和计数规则也由 Rust 提供，避免两端以及小组件各维护一份业务判断。

自动刷新继续只读本地 Git 状态，不自动 Fetch。`remote_ahead` 反映本地已有的远端跟踪信息，不应描述为已经实时询问服务器。Pull / Push 的确认和执行前状态检查仍由核心校验，不能只依赖按钮显示。

共享契约覆盖：五种 Git 关系、读取失败、无 origin、无初始提交、detached HEAD、中文路径、所选平台支持的长路径、新设置的损坏处理、分组 / 计数 / 排序，以及操作可用性。`no_remote` 始终最后；Fetch 允许已配置 origin 但尚无提交的仓库。

全局刷新失败保留最后成功数据，分别记录本次尝试时间、最后成功时间和失败状态；单仓库失败显示该仓库的读取错误。Widget 显示最后成功时间与必要的过期 / 失败提示，不能用一次失败扫描的完成时间把旧数据标成“刚刚更新”。原型先采用以下过期判断：开启定时刷新时，超过两个配置刷新间隔没有成功快照即标记过期；关闭定时刷新时明确显示手动刷新及更新时间，不暗示存在更新承诺。系统何时重绘该提示仍取决于宿主调度。

## 5. macOS 实施范围

原生应用先实现菜单栏入口、状态视图和设置窗口。SwiftUI 构建内容；菜单栏优先使用所选系统版本正式支持的原生 API，必要时用 AppKit 补充菜单栏和窗口生命周期。窗口、焦点、Space 与 Mission Control 行为遵循平台默认，不设置特殊桌面层级。

验证正常窗口恢复、多显示器切换、输入焦点和无障碍。系统字体和原生控件可按平台使用，图标语义、布局和视觉角色遵循共同设计。以旧版紧凑摘要、展开面板和设置结构为基础升级，不依赖 React 运行时，也不以系统模板替换产品设计。

WidgetKit 工作包括：

1. 复用已有小 / 中 / 大视图和测试思路，适配新模型与系统背景、边距、着色规则，放入原生 Xcode 工程。
2. 主应用经 App Group URL 定位共享容器，原子写入版本化快照；扩展只读，不扫描仓库。
3. 数据写入完成后请求重载时间线；保留合理的时间线兜底，处理缺失、损坏、未知 schema 和过期数据。
4. 显示最后成功扫描时间；通过新原生协议 `gitaview-native://` 打开应用或对应仓库，校验传入标识符。仓库已移除时回到仓库列表。协议和应用身份独立定义，不涉及旧数据迁移。
5. 在正式签名且脱离 Xcode 调试器的安装包中，验证 Widget Gallery 可发现、可添加、可读数据和冷启动跳转。

首版建议 Developer ID 签名 + 公证后以 DMG 分发。App Group 权限、扩展签名和嵌套签名在阶段 0 验证。Mac App Store 另列后续范围：沙箱下访问任意仓库、持久目录授权、Git / 凭据工具 / SSH 行为都需要独立验证，不能从 DMG 可用推导为商店可用。

## 6. Windows 实施范围

应用 UI 使用 C# + WinUI 3。该框架是 Microsoft 推荐的新 Windows 原生桌面 UI 方案；本项目仍需要 Win32 补充托盘和特定窗口行为。[Microsoft：WinUI 3](https://learn.microsoft.com/en-us/windows/apps/winui)

先完成托盘、状态面板、设置、文件选择、单实例和协议激活。以主应用作为核心引擎唯一持有者。固定 Rust DLL 搜索位置，确保 x64 应用和 DLL 架构匹配；退出后不留下扫描线程或子进程。

Windows 的原生集成分别交付：

| 组件 | 方案 | 验收重点 |
| --- | --- | --- |
| 官方系统小组件 | C# Widget Provider、Adaptive Cards、包清单注册、MSIX 包身份 | Widgets Board 可发现 / 添加，三种尺寸、状态更新、深链打开应用 |
| 托盘与应用窗口 | 正式 Win32 托盘 API + WinUI 3 正常窗口 | 单实例、托盘激活、关闭驻留、退出及正常窗口 DPI 行为 |

Widget Provider 使用同一 MSIX 包中的独立可执行进程，只读主应用快照，不加载扫描引擎。阶段 0 确定双方可读写的包数据目录，并用安装后的主应用实际写入、Provider 实际读取证明访问成立。首版点击打开主应用刷新，不增加自定义进程间命令通道。

当前 `widget_data.rs` 在 Windows 上为空操作，需要增加 Windows 快照发布适配。主应用原子写入精简快照；Provider 在创建、Activate 和尺寸上下文变化时读取最新数据，活跃期间监听包含该文件的目录并合并更新，以适配原子替换。处理监听溢出、快速连续写入和读写竞争；Deactivate 后没有其他活跃实例时停止监听，重新 Activate 时无条件重读。Provider 被系统回收后不要求继续运行。每个小组件实例分别跟踪上下文，不将进程存活等同于组件活跃。[Microsoft：Provider 生命周期与更新](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-cs)

活跃期间还需安排过期边界更新，保证主应用退出且文件不再变化时仍能提交过期提示；全部失活后取消计时，重新激活时重算。Provider 重启恢复现有实例，异步更新只保留回调内复制的普通值。两端主程序冷启动尚未首刷时，保留配置版本匹配的新原生 Widget 缓存；配置变化则及时重投影，不能保留已删除的仓库。

两端 Widget 快照只包含展示所需字段，不复制本地路径、远端凭据或原始 Git 错误输出。缺失快照、读取失败、未知 schema 与历史数据过期分别显示明确状态。

官方 Widget Provider 的注册需要打包应用与清单，因此采用 MSIX 为首版 Windows 安装方式。在干净机器验证 .NET / Windows App SDK 运行时依赖，以及主应用和 Provider 的 COM / 包清单激活；同一发布版本的原生文件一并打包。无需从旧 MSI / EXE 升级或导入设置。[Microsoft：Implement a widget provider in C#](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-cs)、[Packaged deployment](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/deploy-packaged-apps)

不实现 Progman / WorkerW、跨进程 `SetParent` 或“Win+D 后窗口仍贴在桌面”的要求。Explorer 重启只验证标准托盘图标恢复，不恢复桌面贴附。缩放、多显示器与键盘输入仍需在正常 WinUI 窗口上验证，这些属于原生应用自身的正确性。

## 7. 分阶段交付与估算

以下是基于代码阅读的初步工程量估算，按 1 名熟悉 Rust、SwiftUI 和 WinUI 的开发者全职投入计算；不是性能测量或交付承诺。每阶段区间包含实现与必要验证，不含账号 / 证书办理、商店审核和等待外部资源的时间。

阶段 0 的各平台原型分别需要本平台构建 / 测试设备、稳定工具链与签名条件。缺少某平台时继续共享核心和另一平台工作；该平台的正式 UI / 组件仍须在对应原型验证后推进。无签名开发构建不能替代签名安装包的小组件发现与权限验收。

| 阶段 | 工作内容与产物 | 退出条件 | 估算 |
| --- | --- | --- | --- |
| 0：关键路径验证 | 确定工具链 / OS / 架构矩阵；两端调用最小 Rust 接口；签名 WidgetKit 读 App Group；安装 MSIX 并激活 Provider | 两端显示真实仓库状态；主应用写入的快照可由两端组件读取；组件可添加且深链可激活主应用 | 5–8 人日 |
| 1：共享核心 | 建立 Cargo workspace；提取应用服务、设置和刷新；定义新模型；增加关闭路径 | core 不依赖 Tauri；业务回归通过；新配置可独立读写；无 UI 的测试宿主能启动和停止引擎 | 5–8 人日 |
| 2：跨语言适配 | C ABI、JSON 契约、Swift / C# 包装、快照等待、生命周期与错误处理 | 两端可管理仓库、读取快照和执行受保护操作；在途调用与退出语义通过集成测试 | 5–8 人日 |
| 3：macOS 原生版本 | 菜单栏、完整状态 / 设置 UI、WidgetKit、新配置目录、DMG | 首发架构安装与原生交互验收通过；三种尺寸、失败 / 过期状态与深链可用 | 6–9 人日 |
| 4：Windows 原生版本 | 托盘、完整状态 / 设置 UI、Widget Provider 生命周期、MSIX | 原生窗口、托盘、三种组件尺寸及 Activate / Deactivate / 重启后更新通过 | 7–10 人日 |
| 5：集成与正式发布 | 独立原生 CI、签名、公证、干净安装、性能对比、产品规格与发布文档 | 不依赖开发环境即可安装运行；性能记录完整；无阻断缺陷 | 5–8 人日 |

合计约 33–51 人日，即单人约 7–11 个工作周。删掉数据迁移、旧桌面层和 Tauri 再适配后下调范围，同时将阶段 0 从原来的 3–5 人日调整为 5–8 人日，以计入两端真实安装、签名和组件激活。这里的区间不代表未经原型验证的技术风险已经消失；阶段 0 完成后按实际结果重新估算。

若有两名分别熟悉 Apple / Windows 的开发者，阶段 3 / 4 可以并行；共享核心与契约仍是依赖，日历时间不能简单减半。系统 API 无法满足某项展示要求时，调整产品要求，不增加自定义桌面宿主或非公开 API 作为补偿。

执行顺序为：共享范围与最小契约 → 可用平台原型及核心拆分 → 正式 FFI → 已满足依赖的平台原生实现 → 双平台验收。阶段 0 只调用最小接口并显示一份真实状态，不提前实现完整 FFI 和 UI；其代码保留供后续扩展。按实际环境选择先做 macOS 或 Windows；两端的签名和组件激活均在各自原型中验证，不能让一端缺环境阻塞独立任务。

## 8. 配置、构建与发布边界

- 原生应用首次启动使用空仓库列表和新默认设置，不读取、导入、修改或清理旧 Tauri 数据。不实现 migration marker、旧配置解析、跨版本数据回退或旧安装升级。
- macOS 设置放在新应用自己的标准数据目录，Widget 快照放在 App Group；Windows 使用所选 MSIX 包的标准数据目录。阶段 0 固定原生应用 / 扩展 / 包身份及路径，避免意外复用旧设置。
- 只保证新原生应用自身的单实例与设置写入一致性；不为旧 Tauri 进程增加跨版本互斥协议。首次分发以干净安装为验收场景。
- Rust 核心、FFI、两个宿主与 Widget 契约按同一发布版本构建。保留 schema 和 ABI 自检以发现打包错误或本次原生应用的损坏快照，不承担历史客户端互通。
- 新增独立原生 CI / 发布流程。当前 Tauri 流程保持原状供参考，原生构建不依赖 npm / Vite，不把旧客户端测试全绿作为原生交付门槛。
- 自动更新通道、Mac App Store、Windows ARM64、自选分组的小组件与应用退出后的独立扫描属于后续范围，不计入首版验收。
- 在实施阶段同步更新产品规格，明确新原生范围。现有 `DESIGN_AND_BUILD_SPEC.md` 和桌面层计划描述旧 Tauri 产品，不沿用其技术栈、窗口层级和特殊拖动要求；视觉与信息结构从当前旧版代码提取，按共同设计升级。

## 9. 验证与发布标准

Git 业务规则以现有实现和有效测试为参考，窗口与组件交互以本计划和平台原生行为为准。新增行为修复先补回归测试；提取核心复用相关业务测试，文件名 / Tauri 命令文本断言不计作原生功能验证。

自动化必须覆盖：Rust 核心测试；新契约 fixture 的 Swift / C# 解码；错误码与五种关系 / 读取失败；FFI 缓冲区和句柄生命周期；刷新请求合并 / 会话与代数判断；配置冲突；Git 操作确认及执行前校验；假 Git 超时 / 部分失败后的刷新；退出时唤醒等待者与回收在途调用；原生 UI 的关键交互；真实 Git 临时仓库的集成测试。

原生 CI 运行独立 core 的测试 / fmt / clippy、macOS Xcode 构建 / 测试、Windows dotnet 构建 / 测试与 MSIX 打包。业务测试随核心一起提取，不为复用测试继续依赖 Tauri 运行时。发布必须分别完成 macOS 主应用及扩展签名 / 公证、Windows MSIX 签名与干净机器安装验证。

真机验收至少包含：

- 阶段 0 确定的每个首发架构分别安装启动；首次为空仓库；扫描、添加 / 移除、分组、筛选、计数、设置保存均正确。
- Fetch 无交互卡死；Pull / Push 未确认时核心拒绝；操作失败能恢复 UI；操作结束后刷新状态；小组件按各自宿主生命周期消费快照。
- 无 Git、Git 仅在非默认路径、SSH / HTTPS 凭据失败、断网、仓库删除、中文路径、worktree 和无初始提交的行为明确。
- 菜单栏 / 托盘单实例、冷启动 / 热启动深链、退出、休眠唤醒、开机启动及多显示器恢复符合设计。
- macOS：正常窗口 / 菜单栏交互、Widget Gallery、App Group 读取、签名后的小组件更新；不验收旧桌面层行为。
- Windows：正常 WinUI 窗口、Explorer 重启后的托盘恢复、100% / 150% / 200% 原生 DPI、Widget Board 可发现与重新激活、MSIX 运行时部署。
- 主应用关闭窗口后继续扫描，显式退出后停止扫描；两端组件缺失 / 损坏数据、失败与过期提示正确；主应用重新启动后组件消费新会话数据。
- VoiceOver / Narrator、键盘操作、系统缩放、深浅色、减少动画；状态必须有文本和数量。

性能在目标机器记录新原生版本的冷启动、空闲 CPU / 内存、1 / 20 / 100 个测试仓库的刷新耗时与进程数量，并记录主应用、系统组件 Provider 等全部相关应用进程。可在相同机器上对现有版本做参考测量，但不以复刻旧窗口行为为对比前提。原生 UI 不自动等于更省内存或更快；数值目标在获得原型基线后制定。

小组件验收区分“快照已写入且通知已提交”和“系统已显示新内容”。前者可设应用内目标，后者记录脱离调试器的实际观察，不把系统调度延迟包装成固定时限。

当前 `docs/platform-acceptance-checklist.md` 属于旧桌面 widget，其结果仍为 `_TBD_`。新建原生验收清单，仅保留适用项目，填写 OS 版本、安装包、测试者、日期和失败复现步骤。平台原生支持范围决定功能边界，仍需证明本应用在所声明的首发矩阵上工作正常。
