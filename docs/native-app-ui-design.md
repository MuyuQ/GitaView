# 原生版统一界面设计要求

日期：2026-10-24；2026-10-25 根据用户对当前 UI 的否定反馈修订。用户已明确：**macOS 和 Windows 应统一界面设计，在原有设计的基础上升级。** 本文替换此前方案中“不复刻旧 React 布局”“布局分别按平台控件组织”等放宽视觉范围的表述。当前 Windows 实现没有通过视觉验收，组件名称及排列接近旧版不能视为设计完成。

本文是交给 GLM 的界面实现约束，不代表已经完成界面改造或视觉验收。技术实现继续使用 SwiftUI / AppKit 和 WinUI 3；旧数据迁移、WorkerW、特殊桌面层和旧安装兼容仍不在范围内。

## 1. 统一到什么程度

两端采用同一个产品布局、组件语义、信息顺序和视觉系统。用户从 Windows 切换到 macOS，仍应认得同一个 GitaView，不需要重新寻找筛选、设置和仓库操作入口。

| 两端统一 | 允许的平台差异 |
| --- | --- |
| 状态摘要、标题 / 刷新时间 / 搜索 / 工具入口的结构 | 系统标题栏、窗口按钮、菜单栏与托盘 |
| 分组与状态筛选的位置、排列、计数规则 | 原生控件内部字体度量、焦点环和无障碍机制 |
| 仓库表格列、行选择、行内操作展开方式 | 文件夹选择器、系统权限及启动项设置入口 |
| 设置的信息架构、分区名称和操作流程 | 原生确认框的按钮顺序与系统快捷键约定 |
| 颜色语义、视觉密度、间距层级、图标含义和文案 | WidgetKit / Widgets Board 的尺寸、系统边距和调度 |
| 加载、失败、空态、pending、操作忙态的呈现原则 | 系统深浅色 / 高对比度 / Widget 着色下必要的颜色映射 |

“原生”描述实现框架与系统能力，不授权两端各自采用另一套产品设计。不要求字体光栅化或系统窗口装饰逐像素相同，也不能据此更换主要布局或导航结构。

## 2. 以当前旧版实现为设计基线

先读当前工作区实际组件，不只读历史规格。旧规格与代码存在差异时，视觉与操作结构以当前代码为起点，业务规则以原生实施说明为准。

| 旧版入口 | 保留或升级的内容 |
| --- | --- |
| `src/App.tsx` | 紧凑摘要、展开明细、设置的层次关系 |
| `src/components/WidgetCollapsed.tsx`、`src/lib/collapsedSummary.ts` | GitaView 品牌、仓库总数、待同步 / 需关注 / 无远端的安静摘要；刷新失败提示 |
| `src/components/WidgetExpanded.tsx` | 标题与刷新时间、搜索、刷新 / 设置 / 收起入口；分组筛选在状态筛选之前 |
| `src/components/GroupFilters.tsx`、`StatusFilters.tsx` | 带计数的轻量筛选项、选中态、状态与组的联动 |
| `src/components/RepoTable.tsx`、`RepoActions.tsx` | 对齐的仓库表格，选中一行后只在该行下方展开动作，不在每行常驻五个按钮 |
| `src/components/settings/SettingsShell.tsx` | “仓库设置 / 常规设置”的设置分区及返回路径；仓库、分组与常规偏好各自归位 |
| `src/styles/tokens.css`、`widget.css`、`settings.css` | 浅石墨色、低噪声表面、细分隔线、紧凑控件、中文可读性及稳定对齐 |

不要继续把当前 Windows 的通用 NavigationView 双页模板当作最终视觉基线。可以保留其生命周期与服务接线，按本共同设计替换内容和导航。也不要将未来 macOS 工程独立设计成另一种侧栏应用。

## 3. 共同页面结构

### 状态明细

```text
┌ 仓库状态 / 最近成功读取时间 ─ 搜索 ─ 刷新 · 设置 · 收起 ┐
│ 全部分组及各分组：名称 + 数量，选中态明确                │
│ 全部 / 读取失败 / 分叉 / 远程领先 / 本地领先 / 同步 / 无远端│
├ 状态 · 仓库 · 分类 · 分支 · 关系 · 提交差异 · 提示 ───────┤
│ 仓库行                                                 │
│ 选中仓库行                                             │
│   目录 · 远端 · Fetch · Pull · Push · 操作反馈            │
│ 其他仓库行                                             │
└────────────────────────────────────────────────────────┘
```

这是结构约定，不是已经确认的新像素稿。旧版可见信息和逐级展开方式要保留；升级用于提高层级、对齐、可读性与缩放表现，不增加装饰性仪表盘、大卡片或大面积平台模板导航。

紧凑摘要作为共享组件，用于主应用的紧凑显示模式。明细页不再额外常驻一行完整的“GitaView · 总数 · 待同步 · 需关注 · 无远端”，避免品牌与统计重复堆叠；结果数量需要时放到筛选或结果辅助信息中。紧凑 / 明细是可切换的内容呈现层次，不重新引入旧桌面贴附。由正常原生窗口承载，主程序可以从菜单栏 / 托盘打开；不要求继承旧 312×40 的外层窗口尺寸。系统小组件是独立宿主，不与主程序的紧凑模式混为一项功能。仅在明细页添加摘要 TextBlock 不等于完成紧凑模式。

两端采用相同列顺序。窄窗口先降低次要列占用或横向滚动，保留仓库身份、关系、选中操作和错误入口；宽窗口增加列空间。不得让一端变成卡片墙，另一端是表格。数字与分支使用等宽字体角色；提交差异只展示已有 ahead / behind，不新增未提交文件扫描。

### 设置

设置保留旧版两类分区：

- 仓库设置：添加仓库、扫描目录与候选选择、已管理仓库的路径 / 分组 / 移除、分组管理。
- 常规设置：刷新策略、默认分组、固定 Pull / Push 确认规则、系统启动状态、外观与小组件使用说明。

设置内可以采用侧栏，但不能为主状态页面新增另一套顶层导航来替代旧版操作关系。保存冲突有可见的重载入口；返回状态页时保留筛选、搜索与行选择上下文。移除仅从管理列表删除，不删除仓库磁盘文件。

## 4. 共同视觉角色

先映射当前代码中已经存在的 token。以下是基线色值，不代表可将状态色直接用于所有小字；文字对比不足时采用深色文字配状态标记，或建立两端相同的可读文字变体。

| 角色 | 旧版基线 |
| --- | --- |
| 正文 ink | `#172033` |
| 次要文字 muted | `#5a6a80` |
| 分隔线 line | `#dce3ec` |
| 内容背景 bg | `#f7f9fc` |
| 同步 green | `#2f9f67` |
| 可同步 amber / 琥珀文字 | `#b57412` / `#8a5a0a` |
| 错误与分叉 red | `#b94736` |
| 无远端 slate | `#64748b` |

GLM 应先提取共同的颜色、字号角色、行高、间距、圆角、边框、图标和交互状态，形成可版本控制的 token 表，再分别映射为 Swift 主题与 WinUI ResourceDictionary。旧 CSS 是设计输入，不是要求把 Web 技术带进原生工程。

两端使用相同的字号角色与间距档位，字体允许使用系统可用的中文字体与等宽字体。控件有一致的默认、悬停、焦点、选中、禁用、忙态和失败态。状态包含文字 / 数字 / 辅助标签，不依赖颜色；悬停与焦点不移动内容。增加触控目标或无障碍缩放时维持原有信息层级。

玻璃、渐变和阴影只沿用有用途的少量层次，不为了“原生”额外叠加装饰。窗口外轮廓服从系统；内容区域的轻边界与视觉密度保持同一产品风格。浅色 / 深色均由同一套语义角色推导，不能分别选择两套配色。

## 5. 平台组件与系统小组件

macOS 菜单栏与 Windows 托盘提供相同命令含义，菜单外观由系统负责。主应用采用共同设计，文件选择、确认框、快捷键、焦点与无障碍接入各平台机制。

WidgetKit 与 Windows Widget Provider 延续同一品牌、状态语义、摘要顺序、更新时间和关注列表层级；按系统支持的尺寸调整密度、行数与边距。系统背景或着色可能改变实际色值，文字与语义仍需一致。不得为追求系统组件逐像素相同而创建非公开桌面宿主。

## 6. GLM 的执行与验收

1. 先列出旧版到新版的组件对应表，以及要升级的具体问题；把当前 Windows 原型与旧版的差异标出，不另起一套风格。
2. 固定共同页面结构与 token 表，再实现一套代表性状态页面和设置页面。Windows 可先落地；macOS 使用同一规格，不等待 Mac 才定义共同设计。
3. 用同一组契约 fixture 验证两端。至少包含混合关系、pending、全局失败保留历史、空列表、长中文名称、长分支、组筛选、单仓库忙态及确认取消。
4. 截图同时记录窗口内容逻辑尺寸、缩放、主题与数据来源，排除系统标题栏差异后比较结构。检查表格列、筛选顺序、行内动作、设置分区和状态层级，不以“能编译”或“原生控件默认长这样”判定视觉通过。
5. 已有平台提交真实运行截图；缺少 Mac 的部分保持待验证。预览或 mock 可以辅助设计，但不能标成已运行的 macOS 界面。
6. N12 / N15 在功能完整、共同设计符合、交互可用后再验收；目前 Windows 原型需要按本约束调整。没有要求现在推倒 Rust 核心，也没有授权恢复旧版数据或桌面层实现。

### 7.2 当前实现的偏差与未完成项

- 表格列宽固定、硬编码最小宽度 820，旧版支持调宽；当前不能标为升级完成。恢复合理的自适应与列宽调整，按第 8 节验证。
- 紧凑 / 明细两级窗口形态未做；明细页摘要文字不能替代该功能。
- 分组归属、默认分组有即时保存路径，刷新策略实际使用保存按钮；此前将三者统称“变更即保存”不准确。修改功能时同步说明，并修复分支审查报告中的设置页问题。
- 缺少当前构建的真实运行截图与交互验收。实现者负责先完成可执行环境内的视觉检查，不能只把验收任务留给用户。

## 8. 当前 UI 的整改要求（2026-10-25）

目标是保留旧版轻量 Git 状态工具的识别度：紧凑、清楚、安静，打开后先看仓库与异常，再展开处理。原生框架继续保留；重做 MainPage、SettingsPage 和内容控件样式，不重写 Rust 业务核心。

### 8.1 先解决整体比例和信息层级

- 系统标题栏负责应用身份与窗口控制。内容工具栏只保留“仓库状态”、次要更新时间、搜索和刷新 / 设置 / 收起入口；设置页只保留返回与“设置”，不再重复拼接 GitaView 品牌。
- 明细页去掉额外的完整摘要文本行。工具栏、两层筛选、仓库数据形成连续区域，不在每层增加卡片或装饰框。
- 恢复独立紧凑模式与明确的展开 / 收起操作；切换保留搜索、筛选和行选择。关闭窗口、收起明细、最小化是不同操作，不复用同一图标或文案。
- 统一主内容左右边界，工具栏、筛选与表格主要内容对齐。仓库名称是数据行的主要识别信息；分支、关系与差异按角色减弱，错误保留明确入口。

### 8.2 控件必须形成同一套视觉语言

- 建立 GvToolbarButton、GvIconButton、GvFilterChip、GvTextInput、GvRepoRow、GvSettingRow 等共享样式，页面不能继续混用局部硬编码小按钮和未经协调的系统默认按钮。
- 工具栏输入框与按钮使用同一高度；数据行统一行高；边框、圆角、内边距和文字基线按同一角色表设置。图标使用一致的 SVG/矢量路径，不使用文字字符“‹”“›”代替图标。
- 实现完整的默认、hover、pressed、focus、selected、disabled、busy、error 状态，不能只修改静态 Background/Foreground 后沿用不匹配的默认模板状态。保留原生键盘操作、焦点环与自动化语义。
- 主数据与可操作标签不得普遍压到 10–11 的逻辑字号；以正文/数据 13、辅助信息 12、页面标题 16–18 为首轮实现值，根据真实原生截图校准。不要直接把旧 Web CSS 的像素字号当成原生视觉等价。
- 用原生语义主题资源分别定义浅色、深色和高对比度。不能用固定浅色背景搭配跟随系统变深的默认输入框、列表选择态或提示弹层。

### 8.3 表格按内容分配空间

- 不再以 `MinWidth=820` 和所有固定列宽作为唯一布局方案。旧 RepoTable 默认列宽合计约 514，仅能作为紧凑程度参考；新的字号与平台度量需要重新测量，不能机械复制该总宽。
- 仓库名与提示列承担剩余空间；分支、分组、关系与数字按内容及合理最小值分配。表头与行共用同一列定义，恢复用户调整列宽的能力。
- 首轮验收使用内容区 760×480、1040×680，以及窄内容区 640×480，单位均为逻辑尺寸，不含系统标题栏。这些是检查场景，不是要求所有平台固定窗口大小。
- 常规尺寸下主要信息和行操作不能必须依赖横向滚动；窄尺寸允许次要列收缩、截断并提供完整信息入口，确实超出后才横向滚动。不要缩小字体硬塞内容。
- 选中操作区的按钮、确认提示与结果分层排布。当前一条横向 StackPanel 同时塞五个动作、两段确认文案和结果的方式必须调整；狭窄时可换行，确认 / 错误独立占据反馈行，不推挤其他仓库列。

### 8.4 设置页按操作任务组织

- 保留“仓库设置 / 常规设置”两区导航，但导航采用同一轻量选择样式，不做两个普通大按钮堆叠。
- 仓库设置：把单仓库添加与目录扫描合并到同一“添加仓库”区域，两个入口明确区分；候选列表仅扫描后出现，加入后提供成功与失败数量，并处理候选列表状态。
- 已管理仓库是主要内容，用稳定的列表行展示名称、路径、分组与移除；分组管理次之。不把每个动作都包成相同白色大卡片。
- 常规设置使用设置行及必要的分隔线，把刷新开关、间隔和保存动作放在同一任务区域；启动项展示系统实际状态。不可修改的安全规则和小组件说明放在辅助说明区域，不能与主要操作争抢层级。
- 保存中、保存成功、保存失败、版本冲突的反馈位置固定。说明文字解释后果，避免每项重复标题或暴露 FFI、schema 等实现信息。

### 8.5 GLM 必须交付的可核对材料

1. 先运行旧版或在现有渲染条件下获取旧界面证据，记录其标题、表格、选中行、设置布局及紧凑模式；无法运行的部分注明限制，用源码测量补充，不伪造截图。
2. 先完成 Windows 一个代表性明细页和仓库设置页，使用混合状态、长中文名、长分支、有分组的非空数据进行原生运行检查，再扩展其余状态。预览稿可辅助决策，不能代替原生实现。
3. 对第 8.3 节三种尺寸检查，并覆盖 100% / 150% / 200% 缩放、浅色 / 深色和键盘焦点。保存实际截图，写明提交号、数据来源、内容逻辑尺寸、缩放与主题；注明是原生运行还是设计预览。

6. Windows 的布局、尺寸角色和控件状态固化后，macOS 复用同一设计规格。缺少 Mac 时保持平台验证待完成，不把 Windows 截图冒充双平台完成。

## 9. 2026-10-25 的 Windows 实现

本次已直接修改 Windows 主程序的状态页、设置页、主题与品牌资产，并恢复紧凑切换。通过独立的 GitaView.UIReview 安装包做了原生运行检查，具体修改、截图、测试与未验证范围见 [native-ui-update.md](native-ui-update.md)。第 7 节保留为上一版实现的历史记录，不再用于描述当前工作区。代码及截图仍需用户审阅；未完成 macOS、完整 DPI 矩阵或全部无障碍验收。

用户随后要求改善字体清晰度、采用沉浸式标题栏并更新视觉。当前共同设计进一步要求：标题区与内容采用连续表面，搜索和常用操作直接进入标题区，窗口按钮保留平台原生机制；正文角色以 14、辅助信息以 13 为新基准。Windows 已使用原生 TitleBar 实现，macOS 后续应以同一信息层级接入原生标题栏和工具栏，不恢复单独的深色标题条。字体判断使用正确分辨率的无损导出及实际窗口；缩小的 JPEG 预览不能作为清晰度验收依据。

用户进一步要求更换应用图标并放大软件名称。品牌源文件改为 `assets/brand/gitaview.svg`：深色圆角底板、浅色 Git 分支线与薄荷绿节点。Windows 标题栏与托盘浮窗使用 SVG，应用 ICO 与安装包 PNG 由 `node scripts/native/generate-brand-assets.mjs` 从同一源文件生成。旧版 Tauri 图标不参与此次替换；macOS 后续接入相同图形，再按平台图标规范导出。

主窗口品牌标识为 28 DIP，名称为 18 DIP 半粗体；设置页标题和浮窗名称采用同一 `GvBrandTitle` 角色。WinUI 默认 TitleBar 的标题引用内部 CaptionTextBlockStyle，不能只修改控件 FontSize 并假定已生效；当前使用公开的 Content 放置明确的名称样式，仍由原生 TitleBar 管理窗口按钮与拖动区域。

自定义品牌区与设置标题显式设置 `TitleBar.IsDragRegion="True"`，保留从名称区域拖动窗口的行为。搜索与操作控件继续接收输入。API 依据：[微软 TitleBar 拖动区域说明](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/title-bar#customize-drag-regions)。
